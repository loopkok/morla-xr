# MORLA XR：Quest 3 操作逻辑与 UI 改造计划

> 后续源码实现与验证状态见 [工作区实现说明](WORKSPACE_IMPLEMENTATION.md)。本文保留设计提案基线；验收清单不因代码已编写而自动勾选。

版本：设计提案 v1.0 · 2026-10-27  
代码基线：`c0fcf73` · Unity `6000.0.65f1` · Meta XR SDK `72.0.0`  
目标：在 Windows 编译、Quest 3 独立运行，服务于 MORLA 机器人遥操作。  
交付范围：产品流程、界面规范、状态设计、代码修改清单、实施顺序与验收要求。本次仅编写计划，未修改运行代码、场景、协议或 APK。

## 1. 推荐方案与设计边界

**启动后直接进入透视工作区；以底部轻量工具栏承载常用动作；把当前大菜单改成按需打开的设置窗口，窗口内部使用左侧分类、右侧内容的布局。**

不建议把完整设置侧栏长期悬挂在视野左侧。遥操时主要注意力应留给真实环境和机器人相机画面；常驻侧栏占据视野，还会增加转头、寻找控件和误触的负担。侧栏适合放在设置窗口里面，工作时收起。

采用你提供的“极简工作区”和“侧栏设置窗口”两张参考图的方向；以实际 Quest 菜单照片中的功能为迁移清单。参考截图里的网页选中文字、问答浮层和说明脚注不属于产品 UI。

借鉴 Apple 的信息层次、留白、分组列表、清晰的选中态，以及空间窗口边缘的轻量工具栏。苹果的 ornament 设计将相关控件放在内容边缘，适合作为本方案的参考；Quest 端仍使用自身的手柄、手部与 Unity UI 实现。[Apple：Ornaments](https://developer.apple.com/design/human-interface-guidelines/ornaments)

整套产品围绕四个相互独立的问题组织：

1. **我在哪里操作？** 透视工作区、设置窗口、视频观察区。
2. **设备在采集什么？** 左右手/手柄、头部、身体、麦克风。
3. **数据是否传到主机？** 位姿、视频和语音分别显示状态。
4. **机器人是否真的在跟随？** 必须来自 MORLA 的实际状态回传，不能用网络连通推断。

界面可以做到“几乎没有 UI”，但不能隐藏当前是否发送位姿、麦克风是否开启，以及已知的机器人跟随状态。

## 2. 当前项目的事实与问题定位

以下结论来自当前源码和序列化配置；不是 APK 真机实测。

### 2.1 启动等待不应直接归因于一个 Logo 动画

- `ProjectSettings/EditorBuildSettings.asset` 只启用了 `Assets/Scenes/Scene.unity`，没有单独的 Logo 场景。
- `ProjectSettings/ProjectSettings.asset` 中 `m_ShowUnitySplashScreen: 1`、`m_ShowUnitySplashLogo: 0`，且配置了 VR Splash Image 和 Android Splash Image。关掉 Unity Logo 并不等于关闭整个 Splash。
- `Assets/Oculus/OculusProjectConfig.asset` 还配置了 Meta System Splash。
- Android manifest 已有 `com.oculus.ossplash.background=passthrough-contextual`。
- `AppManager.Start()` 已调用 `ApplyPassthrough()`；实际照片里的菜单背景也是透视。用户感知中的“Start 后才进入透视”，更准确地说是“大菜单被收起、工作数据开始运行”。
- 目前只找到 `MenuRecenter.Start()` 中用于等待定位的 0.5 秒；没有证据证明存在一个人为设置的长 Logo 倒计时。

**改造重点：减少重复启动画面、缩短首帧准备路径、去除大菜单门槛，同时测量真正的启动耗时。** Meta 系统启动画面的时长取决于应用何时开始渲染，不能简单设置为“固定 0.5 秒”。[Meta：Passthrough Loading Screen](https://developers.meta.com/vr/documentation/unity/unity-customize-passthrough-loading-screens/)

### 2.2 一个按钮承担了过多职责

`AppManager.OnStartStreaming()` 同时做了读取 UI 配置、测试 TCP、保存设置、切换 SHAC/IOBT、隐藏菜单、关闭射线、调整手模型、允许位姿发送、启动视频。

`AppManager.Update()` 将左手菜单键直接映射为 `StopStreaming()`；停止还会关闭视频、打开大菜单、关闭 SHAC。当前不是一个能随时查看设置的工作区，而是“菜单/推流”两个强耦合状态。

此外，`OnStartStreaming()` 虽然声明为 `async`，TCP 检查仍在首次 `await` 前执行 `WaitOne(1 秒)`，可能阻塞 Unity 主线程。单纯重绘按钮无法解决点击后卡顿。

### 2.3 设置展示与运行状态混在一起

- `AppManager` 直接从 Toggle 读取运行配置，UI 控件成了业务状态来源。
- `EnsureTrackingToggleRow()` 在运行时克隆开关、拼接布局，不适合维护统一设计。
- `StatusHud` 每帧显示多行调试文本，而且独立于 `Debug Info` 开关。
- `ShowDebugInfo` 还控制手部/头部数据包里的调试元信息。隐藏日志与改变数据格式必须拆开。
- 当前保存集中在开始发送时，部分开关另行保存；关闭设置就退出应用时，用户可能丢失尚未开始推流的修改。
- `ValidateNetwork()` 的 `System Ready` 不是主机成功接收数据的证明；基于 `internetReachability` 的禁用也不适合直接判断 USB/ADB 本地通道是否可用。

### 2.4 媒体通道并未真正独立

- 视频启动失败与 `VideoStreamManager.FailFatal()` 会走全局断连，位姿发送也随之停止。
- `VoiceAudioStreamer` 使用独立 TCP 8001，但录音仍依赖全局 `isStreaming`。
- 语音回传只有 `type/phase/message`，属于操作结果提示，不是完整、持续的机器人状态订阅。
- 视频信令端口为 8765；WebRTC 媒体是否通过 USB 正常连通还涉及 ICE/媒体路径，不能仅凭端口连通判断视频可用。

### 2.5 追踪能力不能通过 UI 美化“扩展”

当前项目有三种底层组合：Mixed 关闭且 IOBT 关闭；Mixed 开启；IOBT 开启。Mixed/SHAC 与 IOBT 互斥，应保留。Meta 当前 Unity 文档也明确写明多模态与 IOBT/FBS 不兼容。[Meta：Simultaneous Hands and Controllers](https://developers.meta.com/vr/documentation/unity/unity-multimodal/)

不要把“自动”解释成“手、手柄、身体随时全部同时输出”；不要把全身估计的所有关节统一标成直接测量且高置信度。

文档与代码还存在漂移：README 写到 31 个身体关节，但当前 `StreamedJoints` 列表实际列出 29 个；部分说明称限流器全部使用减法，当前手部与身体仍有 `_timer = 0f`。本次 UI 计划以源码为准，不顺带修改这些算法；实施前应另行确认并建立发送节奏基线。

## 3. 新版日常操作流程

### 3.1 启动与首次配置

```text
启动应用
  → 系统必要加载阶段
  → 立即呈现透视工作区、轻量状态条和工具栏
  → 恢复已保存配置，初始化本地追踪
  → 首次使用：显示一张可跳过的“连接 MORLA”小卡片
  → 已有配置：显示上次主机与当前追踪状态
  → 用户连接主机、开始发送；视频按偏好独立启动
```

进入工作区不依赖网络、不依赖机器人上线、不依赖麦克风授权，也不要求先按 Start Streaming。

首次小卡片只包含：连接方式、主机地址、连接按钮、“稍后设置”。追踪模式显示当前预设，可点入设置修改，不一次堆满所有高级参数。USB 方式显示“USB / ADB”，默认端点 `127.0.0.1:8000`；首次说明须配置主机 ADB 转发。

默认恢复追踪配置、窗口位置和显示偏好。**首版不自动发送位姿、不自动恢复机器人跟随、不自动开启首次录音。** 这既能去掉菜单门槛，也兼容目前尚未核实的 MORLA 下游行为。

后续接入 MORLA 状态和控制门控后，可以提供“启动后自动连接主机”；连接默认只用于状态、预览和准备，自动发送必须单独选择，机器人自动使能/自动跟随不在本方案默认行为中。

### 3.2 正常使用

1. 进入工作区，看见真实环境和左右侧追踪状态。
2. 点工具栏主按钮“开始发送”。无可用主机配置时先显示连接卡；连接成功且必要追踪就绪后发送。
3. 若视频已启用，独立连接并展示机器人画面；位姿和视频各自报告真实状态。
4. 机器人使能、工作位和跟随仍按现有 MORLA 流程执行。首版 Quest 不新增虚假的“一键接管机器人”。
5. 需要调整时唤出工具栏，打开设置；按照第 5 节的菜单隔离规则进入操作状态。
6. 关闭设置只关闭窗口，不自动恢复发送或机器人跟随。
7. 点“恢复发送”恢复 Quest 数据；在支持回执的后续版本中，再单独确认恢复机器人跟随。

### 3.3 四种常见行为的明确含义

- **关闭设置**：收起设置窗口，不断开视频，不退出应用。
- **暂停发送**：停止向下游输出位姿/手柄命令数据，本地追踪可继续，视频可继续。
- **断开主机**：停止该主机的位姿、语音和视频会话，保留配置与透视工作区。
- **暂停跟随**：请求 MORLA 暂停机器人跟随，只有拿到实际回执才显示成功。这是后续跨端功能。

“暂停发送”不能命名为“急停”。真正的急停由机器人系统提供，UI 不宣称自身替代硬件/控制器急停。

## 4. 工作区与窗口布局

### 4.1 默认工作区

```text
        [MORLA XR · 主机名称]     [位姿：发送中 | 机器人：状态未接入]


                 真实环境 / 机器人主相机窗口
                  中央区域无大菜单和坐标文本


           [发送/暂停] [视频] [麦克风] [设置]
                     左：手部 · 右：手柄
```

此处是布局示意，不是要求把文字贴在屏幕边角。状态条、工具栏应位于舒适可达的工作区范围内，而不是照抄桌面屏幕四角。

- 标题收小；版本、版权、开发者信息移到“诊断与关于”。
- 正常情况下只显示一行必要状态。点击状态区域可查看位姿、视频、语音各自的明细。
- 工具栏使用图标加短文字，尤其“发送/暂停”始终带文字；不以 Wi-Fi 图标代表 USB 或机器人控制状态。
- 发送按钮：空闲时“开始发送”，运行时“暂停发送”，设置导致暂停后为“恢复发送”，准备中为“正在连接/等待追踪”。同一位置保持稳定。
- 机器人跟随已确认后才显示单独的“暂停跟随”操作；未接入状态服务时明确显示“状态未接入”，不显示假的“未使能”。
- 麦克风开启、位姿发送、关键故障的提示不能因自动收起而消失。
- 工具栏初版保持可见。验收完成后可增加空闲约 5 秒缩成小胶囊的选项；故障或录音时仍保留指示。
- 首版不同时提供多个工具栏、腕部菜单、常驻侧栏和手势快捷菜单，避免操作入口竞争。

### 4.2 设置窗口

```text
┌ MORLA XR  设置                         [关闭] ┐
│                                              │
│ 概览             追踪输入                     │
│ 连接与传输       追踪配置                     │
│ 追踪输入         [标准输入][混合输入][全身]    │
│ 视频与显示                                   │
│ 语音             当前输入：左手部 / 右手柄     │
│ 诊断与关于       输出侧：双侧                  │
│                  头部位姿：开启               │
│                                              │
│                  配置已保存                   │
└──────────────────────────────────────────────┘
```

设置窗口占工作区中间一部分；打开时可将视频移到旁边的次级观察位。追踪/连接变更会在窗口底部解释影响。侧栏约占窗口宽度 23%，主内容约占 77%。不再分别设“网络连接”和“数据传输”两组相近入口，合并为“连接与传输”。

窗口关闭按钮只关闭设置。标题栏拖动用于重新摆放窗口；“回到面前”只改变 UI 位置，不修改 XR tracking origin，也不重标定机器人。

### 4.3 视频窗口

- 视频是机器人观测内容，使用独立面板，支持主画面、缩略预览、隐藏。
- 隐藏画面与停止接收是两个动作：隐藏保留连接便于快速恢复；“停止视频接收”释放媒体资源。
- 多相机沿用现有多 track 能力，主相机一张，辅助相机以可点选的缩略条呈现；没有 track 时不画假相机。
- 保留相机原始宽高比、FOV、主机 `size_multiplier` 约定；不按设计稿像素强行缩放视频内容。
- 窗口标题显示主机提供的相机名；等待首帧时显示“相机已连接，等待画面”。解码开始后才显示“视频播放中”。
- 冻结或断流时给最后一帧添加明显的“画面已中断”覆盖层与本地最后收帧时间，不能让静止旧画面看起来仍是实时画面。
- 可显示接收 FPS、距最后解码帧的时间；没有源端时间戳和校时数据时不显示虚构的端到端延迟。
- 默认视频锚定先沿用已验证的观看行为；新增世界固定/视野跟随作为可选设置，分别测试舒适度和 FOV 表现。

## 5. 菜单交互必须与遥操输入隔离

打开 UI 时，手部捏合、手柄扳机以及手/头移动都可能是机器人输入。只把菜单设为可见而维持原发送逻辑，会让点击菜单的动作传给机器人。

### 5.1 首版：Quest 端独立可实施的规则

1. 左手菜单键或工具栏“设置”触发 `EnterUiInteraction`，先关闭本地所有位姿及手柄按钮的发送门，再允许 UI 执行动作。判定须在同帧各发送器发送前完成。
2. 默认暂停语音采集并清空待发音频，避免在设置中讨论“开始跟随”意外触发已有语音命令；视频继续接收。
3. 窗口提示：“位姿发送已暂停；机器人状态未接入”。不能显示“机器人已停止”。
4. 改参数、关闭窗口均不恢复发送。恢复需要显式操作，释放已按住的扳机/捏合，再取新的有效追踪样本后打开发送门；不得重放排队的旧姿态或音频。
5. 在真实机器人上部署前，必须验证 MORLA 在数据中断/过期时现有的停止跟随和重新接管规则。若该规则不存在或会自动恢复运动，先完成下一节的跨端控制门控。

工具栏内其他需要手势点击的动作也遵守该隔离逻辑；“暂停发送”应在按下入口时立即关闭发送门，不必等按钮松开动画。首版将有效手部/手柄射线命中可交互工具栏区域作为进入 UI 交互态的信号，先关闭发送门，再接受捏合/扳机；恢复按钮则在操作完成、释放输入后重新取有效样本。只有视线扫过不触发。这个保守规则可能造成误悬停暂停，需要真机评估命中区域；隔离承诺从识别到 UI 意图开始，不宣称能提前识别用户尚未指向工具栏的抬手动作。

### 5.2 目标版：接入 MORLA 后的交互

1. 用户进入交互态，Quest 请求暂停跟随，同时禁止 UI 按钮事件成为机器人命令。
2. MORLA 确认已暂停后，UI 显示“跟随已暂停”；必要遥测可继续用于监控或记录，但由 MORLA 控制门阻止其驱动机器人。
3. 未收到回执时显示“等待暂停确认”；超时则显示“暂停未确认”，保持本地停止发送，禁止显示成功。
4. 恢复时检查控制权、追踪有效性和重新对齐条件，经明确操作与主机确认后才显示“跟随中”。

暂停确认超时、数据过期阈值、双臂联动停止策略必须与 MORLA 现有控制周期和 watchdog 一致，不能从 UI 动画时长推导。

### 5.3 Quest 交互适配

- 手柄：保留当前左右射线与扳机操作；左手 Menu 键改为显示/收起工具栏或设置入口，不调用全局停止函数；不占用右手系统 Meta 键。
- 手部：常驻工具栏可通过已有 hand ray + pinch 使用。先完成 SDK 72 下的兼容验证，再考虑可选腕部入口。
- Mixed 模式：当前代码备注已说明 `Touch|Hands` 会使旧 `OVRInputDeviceActiveState` 判定失效。必须修复/替换 UI 射线 active-state 条件，不能靠“打开菜单时关闭 SHAC”维持交互，否则会改动实际追踪模式。
- `ControllerMenuPointer` 启用条件改成 `UiInteractionEnabled`，不能继续写成 `!isStreaming`。只处理注册过的交互画布；状态文字、视频内容和隐藏面板不阻挡射线。
- 保留使用画布 `worldCamera` 的命中方式和已有按下目标捕获机制。增加拖动、ScrollRect 滚动、滑条与系统键盘验证，不能假定现有 Button/Toggle 点击桥已支持全部控件。
- 关闭窗口、追踪丢失或输入设备切换时清理 hover/pressed/drag 状态；恢复时不继承一次未完成的点击。
- 不依赖眼动凝视点击；本项目主交互保持手柄与手部。
- 身体追踪模式的实际 UI 可用性必须真机验证。源码中的“body 与 hand 互斥”注释过于笼统，不能据此把全身模式设计成不支持任何手部操作。

## 6. 设置页面逐项规格

### 6.1 概览

内容按“设备 → 主机 → 数据 → 机器人”排序：

- 设备：Quest 3、当前追踪配置、权限问题。
- 主机：名称或 IP、USB/局域网、连接情况。
- 位姿：未发送/连接中/发送中/部分异常/已暂停；左右侧实际输入和身体是否有效。
- 视频：未开启/连接中/等待首帧/播放中/中断。
- 语音：关闭/等待权限/监听中/重连中/已暂停。
- 机器人：未接入状态服务时只显示“状态未接入”；接入后显示主机实际状态及更新时间。

主按钮只显示当前最相关动作：“配置连接”“开始发送”“恢复发送”。不再用 Quest 设备 Ready 徽章代表整条遥操链路 Ready。

### 6.2 连接与传输

- 连接方式：USB / ADB、局域网 TCP、UDP（高级）。USB 是通过 ADB 转发 TCP，不是新增原生 USB 协议。
- 位姿端点沿用现有默认：USB `127.0.0.1:8000`、局域网端口 `8000`、UDP 广播 `255.255.255.255:9000`。
- 局域网 IP 使用带提示的空输入或历史主机，不再把 `192.168.1.1` 当作已经可用的机器人主机。
- 高级区：视频信令端点默认 8765，语音端点默认 8001；默认跟随主机地址，可独立配置。UDP 广播不能作为视频/语音的单播目标。
- “测试连接”明确只测试端点；“发送中”来自实际发送器状态；UDP 没有接收端确认时显示“正在发送 · 接收未确认”。
- 主机地址支持校验、端口限定 1–65535、去空格。若实现支持域名，必须使用异步解析并明确错误信息。
- IP/端口输入使用适合的键盘，保留历史连接，减少头显打字。
- 修改地址只修改草稿；点击“应用并连接”后切换会话。切换协议记住各自上次地址，不能反复覆盖为默认值。
- 首版自动连接默认关；后续用户主动开启后持久化，仍不代表自动恢复跟随。
- 展示 USB 排错说明：主机运行状态、ADB 设备授权、8000/8001/8765 各服务与转发；视频媒体链路另行验证。

### 6.3 追踪输入

把 `Mixed Input` 和 `IOBT Body` 两个互斥勾选框改成一个三选一配置控件：

1. **标准输入**：Mixed 关、IOBT 关；使用运行时当前的手或手柄输入，不承诺左右异构同时追踪。
2. **手部与手柄混合**：Mixed 开、IOBT 关；保留现有每侧仲裁，一侧手柄在用时该侧手部不重复发布。
3. **全身与当前输入**：Mixed 关、IOBT 开；身体数据加当前有效的手/手柄输入，不承诺 SHAC 式混合共存。

页面紧接着显示实时结果：“左侧：手部；右侧：手柄；身体：未启用/准备中/有效/质量下降”。**配置意图与运行事实分开显示。**

其他设置：

- 输出侧：双侧/仅左侧/仅右侧，替代 `Both Hands` 的含糊称呼。该选择作用于手部及手柄输出，不自动删除身体骨骼中的对应侧关节。
- 头部位姿：独立开关，保留原有输出能力。
- 可选扩展“只输出手部/只输出手柄”：属于新增发送策略，需要新增过滤与回归测试，首版不以仅更改标签的方式宣称支持。
- 身体权限在用户选择全身配置后按需申请；拒绝后保持设置可操作，并明确告知全身不可用，不暗中改成其他模式。
- 追踪模式、输出侧、头部开关会影响下游输入；暂停发送后应用。IOBT 切换还涉及世界/躯干坐标系变化，必须按重配置事务处理。
- 默认迁移上次模式；全新安装延续现项目“全身与当前输入”，若权限未授予显示“等待开启身体权限”，不要卡住工作区。

### 6.4 视频与显示

- 视频接收：开启/关闭，独立于位姿发送。
- 画面显示：主画面/缩略/隐藏；多相机有实际 track 才出现选择器。
- 视频尺寸、位置、重置布局；保留原有 FOV 计算。
- 显示刷新率：72 Hz/90 Hz，显示“请求值”和可获取的“实际值”。不把显示 Hz 当成手部新样本率，也不宣称系统会按代码自动完成所有热降频策略。
- 画质默认沿用 `720p30`。其他画质档只有主机支持并协商成功后才启用；不画无法执行的选项。
- 增强对比、文字大小、减少动画；首次即可调整。
- 刷新率变更可能引发短暂视觉变化，并改变当前与显示帧率耦合的发送节奏；按影响运行的配置处理，不能悄悄热切。
- 默认避免全屏沉浸遮挡真实环境；沉浸显示若后续加入，保留快速回到透视入口。

### 6.5 语音

- 开关命名为“麦克风上行”，说明“音频发送至 MORLA 主机识别”。不暗示 Quest 本地识别。
- 分别展示用户开关、麦克风权限、实际录音、网络发送状态；录音时显示持续可见的麦克风指示。
- 初次默认关闭；已有开启偏好可以保留，但每次是否实际录音仍取决于前台、会话状态及 UI 交互隔离规则。
- 首版保留现有中文指令语义，不新增语音使能、HOME 或工作位动作。
- 反馈区最多显示最近一条结果与展开后的短历史；`submitted` 显示“主机已接收”，`confirmed` 显示“主机已确认”，失败给原因。
- 不从自由文本“遥操已开始”解析出永久机器人状态；跨端状态订阅尚未实现时仅作为一次结果提示。
- 保留当前 16 kHz、PCM16、40 ms 帧、实际采集时间戳与过期丢弃逻辑；UI 改造不能延长音频队列。
- 拒绝权限只影响语音，不阻塞透视、追踪和视频。切后台、失焦、断开主机、停止语音时立即结束录音；恢复需要满足明确的会话条件。

### 6.6 诊断与关于

- 包含实际设备/应用版本、各流连接状态、各源有效样本率、发送率、视频收帧状态、最近错误和日志导出。
- 调试坐标、骨骼点、射线命中信息在此按需开启，工作区默认隐藏。
- 分成“显示调试面板”和“发送协议调试元信息”两个配置；后者迁移原行为，不因 UI 变漂亮而默默改变。
- 无可靠采样数据的指标显示“未测量”，无主机回执的接收率显示“不可用”。TCP 已连通、socket 写入成功、主机接受数据是不同状态。
- 重置窗口布局与恢复全部默认设置分开。恢复默认需一次明确确认，避免误删已配置主机；不建议要求用户卸载来获得新默认值。

## 7. 视觉规范与空间尺寸

以下数值为第一轮设计起点，需要在 Quest 3 双眼实机校准，不是平台硬性规格。

### 7.1 视觉语言

- 默认浅色高遮蔽面板：主面板 `#F4F5F7`，内部内容 `#FFFFFF`，正文 `#1D1D1F`，次级文字 `#5F6368`，分隔线 `#D8DADF`。
- 主操作蓝色 `#0A66D9`；绿色用于已确认正常，琥珀用于等待/降级，红色用于失败和停止类动作。状态始终同时带文字/图形，不只靠颜色。
- 面板透明度约 0.90–0.96；不要复用照片里低对比的大片透明黑底。
- 初版用轻微透明、细描边、圆角形成层次，不要求实时高成本背景模糊或折射。透视由合成层提供时，普通 UI 模糊材质也不一定能读到透视背景。
- 窗口圆角 24–28 逻辑单位，分组 14–18，按钮 12–16；整套控件统一，避免每种按钮不同形状。
- 一个页面仅一个主要蓝色动作；常规设置行用分隔线与留白，不把每个值都包成厚卡片。
- 功能图标采用同一套可用于 Android 的开源/自绘线性图标；字体选有中文覆盖的可分发字体，例如 Noto Sans CJK/思源黑体。不要直接打包 macOS 系统字体或将 SF Symbols 当作通用 Android 资源。

### 7.2 尺寸与可读性

- 设置面板初始距离约 1.1–1.3 m，宽约 0.85–1.0 m；宽 0.9 m、距离 1.2 m 时水平视角约 41°。
- 面板中心略低于水平视线；工具栏中心约在视线下方 15°–20°，用实际伸手/射线可达性调整。
- 可用 1000×680 逻辑单位搭建设置面板，再统一缩放到上述空间尺寸；这不是头显屏幕分辨率。
- 正文 26–30、次级说明不低于 22–24、页标题 36–40 逻辑单位。长文字分行，不靠无限缩小字体塞进一行。
- 主要行高 64–72，按钮命中区至少约 64×64 逻辑单位；在上述尺寸下约对应 2.7° 的点击目标。视觉图标可更小，命中区保持足够大。
- 按钮之间保留 12–16 逻辑单位空隙，工具栏图标加文字后保证宽度；最终以近/远视力使用者和手部抖动测试为准。
- TMP 构建中文 SDF 与 fallback；必须覆盖配置文案和主机动态中文反馈。检查字重、截断、缺字、长 IP、长错误消息。

### 7.3 动效与锚定

- 开关、选中反馈 100–160 ms；窗口出现/收起 150–220 ms；仅轻微透明度或位移变化，不做大幅弹跳。
- 等待用小型进度指示和具体阶段文本，不使用假百分比。
- 默认窗口在唤出位置稳定，避免紧贴头部、每次转头都立即追随。可提供延迟跟随，但有停留阈值和死区，不能始终在视野中漂移。
- 世界固定窗口越出可见范围时，保留菜单键和“回到面前”入口。纯手部模式保留一个可访问的小入口。
- 视频、设置、状态条分别管理层级，避免互相穿插。必要时将设置置前并把视频放到侧边，不能突然遮掉关键告警。
- “减少动画”关闭位移/缩放，仅保留必要状态反馈。

## 8. 状态模型与异常处理

### 8.1 不再以一个 `isStreaming` 表示整个产品

建议使用以下互相独立的状态域，UI 读取统一快照。以下名称是拟新增设计，不是现有 API：

```text
WorkspaceState   Initializing / Ready / Suspended
TrackingState    Unavailable / Preparing / Valid / Degraded
TelemetryState   Idle / Connecting / Sending / Paused / Faulted
VideoState       Off / Connecting / WaitingFrame / Playing / Stale / Faulted
VoiceState       Off / PermissionRequired / Connecting / Listening / Paused / Faulted
UiState          Compact / Toolbar / Settings
RobotState       Unknown / Unavailable / Ready / Following / Paused / Faulted
```

`TrackingState` 还应有左手、右手、头部、身体各自的来源、有效性和采样时间。`RobotState` 是未来主机状态的 UI 投影，不应假设机器人“使能/跟随/采集”互斥；模型内部另存 enable、follow、recording、owner 等独立字段，按主机真实契约映射。

核心约束：

- `UiState.Settings` 不等于网络断开。
- `VideoState.Playing` 不要求 `TelemetryState.Sending`。
- 本地追踪可运行而不向外发送。
- TCP 连接成功不直接推出 `RobotState.Ready`。
- 声音反馈成功不直接推出持续 `RobotState.Following`。
- 网络恢复、应用恢复前台、关闭设置都不自动恢复跟随。
- 请求模式与实际已应用模式分别保存；未完成切换时不得用新模式标签描述旧坐标数据。

### 8.2 关键状态转移

```text
本地工作区
  ├─ 开始发送 → 校验配置 → 建立实际通道 → 必要追踪就绪 → 发送中
  ├─ 打开视频 → 信令与 WebRTC 连接 → 等待首帧 → 播放中
  └─ 开启麦克风 → 权限 → 采集与连接 → 监听中

发送中
  ├─ 打开设置 / 交互隔离 → 暂停发送；保持工作区和可用视频
  ├─ 必要输入失效 → 暂停发送；标明具体输入原因
  ├─ 关键视角失效 → 按预设策略暂停发送/请求暂停跟随
  ├─ 位姿通道故障 → 暂停发送；显示原因与重连入口
  └─ 切后台 / 头显摘下 → 暂停发送与录音

暂停发送
  └─ 明确恢复 + 配置一致 + 新鲜追踪有效 + 必要链路恢复 → 发送中
```

“必要输入”由当前使用配置确定。首版未接入机器人能力声明时，按用户启用的输出侧、头部与身体项目判定；有任一必要源失效时整体暂停，避免未验证的单臂继续运行。后续独立机械臂策略由 MORLA 声明和确认。

### 8.3 故障呈现规则

- 主机未启动：保持透视和本地追踪。提示“无法连接 MORLA 主机”，次级文字给端点，提供“重试”“编辑连接”。
- USB 无转发：显示 USB 专用排错信息，不提示用户去连接 Wi-Fi。
- 位姿某个 socket 故障：聚合成实际通道错误，关闭必要输出的发送门。当前每个 streamer 可独立建连接，不能只看一个探测 socket。
- 视频失效：停止/重试视频通道，不调用一键关闭所有服务的全局函数。**但通道独立不等于允许机器人盲操**：视频启用的遥操配置默认将主视角设为必要条件，失败会暂停发送并在接入主机后请求暂停跟随；旁路辅助视频才仅提示。该策略在暂停状态下配置。
- 麦克风权限拒绝、语音服务离线：仅语音不可用，其他通道不因这个原因被全局关闭。
- 身体质量降低：显示真实状态；是否暂停由当前必要质量门槛决定，不把请求 High 当成实际 High。
- 追踪恢复：状态可自动恢复有效，发送/跟随保留显式恢复门。
- 网络重试：后续可采用 1、2、4、8 秒上限的退避连接（可加抖动）；只恢复通道，不恢复运动权限。用户断开后停止重试。
- 普通提示约 3 秒消失；阻塞操作的错误持续显示，恢复后转为恢复提示；重复错误合并。
- 同时出现多个问题时按“控制/必要输入 → 位姿 → 关键视频 → 其他媒体”排序，不弹出多个对话框。

### 8.4 坐标与追踪切换事务

当前 `BodyPoseStreamer.ToBodyRelative()` 在没有身体参考时会原样返回世界坐标。因此本地追踪提前启动之后，不能只等一个 Toggle 打开便立即发 IOBT 模式数据。

切换步骤固定为：关闭发送门 → 暂停并确认下游控制（若支持）→ 更新追踪配置 → 清除旧缓存/旧参考 → 等待新模式和新身体参考有效 → 确认输出坐标系一致 → 提示重新对齐/接管 → 用户恢复。

保留 `_hipsBoneToTorsoFix`、左右手骨轴约定、hips 世界系与其他关节躯干系的协议语义。参考姿态必须带有效时间；追踪丢失后不能无限使用陈旧 hips。UI 重定位不能调用会改变该坐标系的全局重定位 API。

## 9. 启动优化的具体工作

### 9.1 第一轮：保留单场景，缩短首帧路径

1. 在 Windows Unity 的 Player / Splash Image 面板关闭重复的内置 Splash，并检查 VR Splash Image 是否仍在显示同一图。同步检查 Android Splash Image 与 Meta System Splash，避免多层连续出现。
2. Meta 系统加载画面只保留一份简洁 MORLA 标识，沿用已有 `passthrough-contextual`。系统主页没有开启透视时，这个 contextual 设置不保证启动背景一定透视。
3. 删除任何仅为品牌展示而增加的自定义等待；当前没有发现独立的长延时脚本，不能凭空删一个“Logo 场景”。
4. 让透视与最小 UI 初始化独立于网络配置控件。当前 `AppManager.Start()` 在 `ApplyPassthrough()` 前访问 InputField 和载入配置，应避免 UI 引用异常让透视初始化被跳过。
5. 场景默认不激活旧大菜单。先显示 WorkspaceShell；按需实例化设置页面、诊断面板和骨骼调试对象。
6. 网络检查、视频协商、麦克风申请不阻塞进入工作区；所有阻塞连接移出主线程。
7. 0.5 秒菜单重定位等待改成“有效头部姿态到达后摆放 UI”，有超时与可重试入口，而非把固定延时当作定位有效证明。

Meta 的加载屏说明支持关闭内置 Splash、清除 VR Splash Image 并采用系统透视加载；实施以 Unity 6000.0.65f1 实际 Player 面板与生成 APK 为准。文档中的旧订阅限制文字不作为当前许可证结论。[Meta：加载屏配置](https://developers.meta.com/vr/documentation/unity/unity-customize-passthrough-loading-screens/)

### 9.2 第二轮：有测量证据再拆启动场景

只有确认当前大场景/资源加载主导等待后，才新增轻量 `Bootstrap` 场景并异步加载工作区内容。保证只有一个 XR Rig、OVRManager、EventSystem 和服务容器，避免叠加加载重复创建 XR 实例。重构期间不同时升级 XR SDK 与 Unity 引擎。

埋点至少包含：Android 启动事件、最早可观测 Unity 生命周期、工作区首帧、透视可用、首个有效追踪样本、实际通道就绪、视频首帧。早于 Unity 的阶段用 adb/logcat 与录屏关联，不能用 `AppManager.Start()` 时间代替完整冷启动耗时。

目标是“没有人为 Logo 停留，工作区不等待外部网络”，不是未经测量承诺冷启动一定少于 2 秒。冷启动和热启动分别测量中位数/p95，再为本机 APK 建立目标。

## 10. 代码与场景修改清单

### 10.1 新增的最小职责划分

避免一开始写十几个空壳管理器。首轮采用以下六个业务职责，可按需要分文件：

- `AppSettings` + `SettingsStore`：类型化配置、schemaVersion、旧偏好迁移、保存/草稿/当前生效配置。
- `SessionCoordinator`：启动、暂停、断开、生命周期与模式切换事务；维护当前操作代次，丢弃失效异步回调。
- `TrackingCoordinator`：本地追踪启停、模式互斥、输入仲裁和各源有效状态；不负责画 UI。
- `SessionStatus`：汇总各实际通道与追踪状态，产出只读快照/事件；不解析 HUD 字符串来推断状态。
- `WorkspaceUIController`：工作区、设置导航、工具栏、状态提示和窗口位置。
- `UiInteractionGate`：处理 UI 意图、输入消费、发送门和恢复条件；以后接入 MORLA 暂停/恢复回执。

保留现有位姿 streamer 和媒体服务作为适配层；第一轮不把多个 TCP 连接强行合成一个，以免改变下游接收器假设。

### 10.2 `Assets/Scripts/AppManager.cs`

主要入口：`Start()`、`EnsureTrackingToggleRow()`、`SaveConfig/LoadConfig()`、`Update()`、`OnStartStreaming()`、`HandleDisconnection()`、`StopStreaming()`。

- 先变成兼容入口，把 UI 查询和业务决策逐步迁到上述职责。
- 替换 `isStreaming` 对追踪、射线、视频、语音的总开关作用。过渡期可留只读兼容属性，但每个调用方必须有明确的新状态来源。
- 拆分 `StartTelemetryAsync`、`PauseTelemetry`、`DisconnectHostAsync`、`OpenSettings`；方法名按实际职责命名。
- 移除“打开菜单就关闭视频/SHAC”的副作用。
- 将阻塞 `WaitOne` 换成受控异步连接，支持超时、取消和重复点击去重；不能以改成 `async void` 代替异步实现。
- 不再通过每帧覆盖 `System Ready` 更新状态，改成状态变化驱动。
- 用真实发送器事件更新各流状态；连接探测的成功不能直接作为全局 Sending。
- 移除运行时克隆 Toggle 布局，保留显式 prefab 与序列化引用。
- 任一 UI 页面没实例化时，业务仍能从 `AppSettings` 读取配置，不能空引用或被当成默认开启。

### 10.3 四类位姿发送器

涉及 `HandLandmarkStreamer.cs`、`ControllerPoseStreamer.cs`、`HeadPoseStreamer.cs`、`BodyPoseStreamer.cs`。

- 将“读取追踪/维护有效性”和“打开 socket/发送”分离，允许离线预览。手部继续使用现有更新事件，其他源保留现有采样方式。
- 所有发包前检查统一发送门，包括按钮行、头部、身体；不能只停止手腕包。
- 增加结构化状态事件：来源、有效性、最后采样时刻、实际连接/写入错误。健康信息不再来自日志文案。
- UI 模式切换不能改变手柄在手判定的分支逻辑。当前 `IsControllerActive`/SHAC 条件依赖“推流中”；本地预览上线后应改为“实际 SHAC 生效”，并为非 SHAC 保留原有代理判定。
- 停止发送时主动清理连接/队列；不要依赖下一次手部更新才断开，因为追踪丢失后事件可能不再到达。
- 避免在主线程执行阻塞 `Connect/Write`。首轮盘点所有同步 I/O；如引入后台发送，使用有界队列、最新样本优先和原始采样时间，不让网络慢导致陈旧姿态排队。
- 保留包头、payload、精度、坐标转换、按源序列和校时握手。发送线程改造单独回归，不与 UI 样式一起无差别重写。
- `BodyPoseStreamer` 的 `OVRBody` 懒创建、权限和参考姿态维护由 TrackingCoordinator 协调；仍坚持 SHAC/IOBT 互斥。

### 10.4 `ControllerMenuPointer.cs` 与 `MenuRecenter.cs`

- 显式注册新工具栏、设置窗口和可操作视频边框，避免 `FindFirstObjectByType<Canvas>()` 随机选中画布。
- 对 UI Canvas 添加/检查正确的 `GraphicRaycaster`、相机与 EventSystem 引用。
- 继续支持左右手柄；新增滚动、滑条、窗口拖拽的真实事件处理。
- 将输入门控早于发送执行，统一处理菜单按键在原 buttons bitmask 中的消费策略。若下游依赖该 bit，必须同步确认行为变更；不得假设它无人使用。
- `MenuRecenter` 改为通用窗口摆放服务，只移动 UI，不改变追踪原点。防止低头/抬头导致 forward 投影退化时跳到错误位置。

### 10.5 `StatusHud.cs`、`LogDisplayHands.cs`、`LogDisplayNetwork.cs`

- 业务状态条替代现有常驻多行 HUD；原 HUD 转成诊断面板。
- 本地 UI 设置 `ShowDiagnostics` 与原协议调试字段开关分离。
- UI 文本按状态变化或 5–10 Hz 刷新，避免每个 90 Hz 渲染帧重建长字符串和布局。
- 骨骼/关键点视觉默认隐藏，但诊断中可开启；`HandLandmarkVisualizer` 由“本地追踪有效＋可视化开关”驱动，解除对发送状态的依赖。
- 动态中文反馈使用明确的字体资源，不能随机找一个 TMP Text 的字体。

### 10.6 视频相关脚本

涉及 `VideoStreamManager.cs`、`VideoPanelRenderer.cs`、`VideoStatsOverlay.cs`、`QuestVideoReceiver.cs`。

- `StartVideoSession/StopVideoSession` 独立于位姿启停，UI 订阅媒体状态。
- 修改 `FailFatal()` 的全局断连调用，改为发出 VideoFault；SessionCoordinator 再按“是否关键视角”决定位姿/控制动作。
- `SetVideoUiVisible()` 只决定显示，不隐式断连接；独立的停止接收操作释放资源。
- 新增最后解码帧时间与冻结提示；不把网络有字节到达当成画面持续更新。
- 保留多轨、主机布局配置、FOV 和静音/不可见轨行为。没有视频的轨不保留伪“实时”缩略图。
- 异步启动/停止须串行化或取消；“启动视频→立刻断开→旧 await 完成”不能重新弹回视频窗口。

### 10.7 `VoiceAudioStreamer.cs`

- 从全局 `isStreaming` 条件迁移到语音自身会话条件与 UiInteractionGate；保证前台、授权、用户开关共同生效。
- 发送结构化 `VoiceStatus` 和结果事件，替代只提供静态 `HudLine`。
- 优先修复 `StopCapture()` 的主线程 `Thread.Join(1300)` 等可能卡顿点：先立即结束录音/禁止发送，再异步等待线程结束；重复停止必须幂等。
- 保留短队列、过期丢弃、实际采集时间戳；不能把关闭设置后残留的音频发回去。
- 停止旧线程后才允许新会话接管，避免重连线程、旧反馈和新主机混用。

替换旧菜单时先解绑旧事件，再禁用旧根节点；迁移完所有业务对旧 Toggle/InputField 的读取之后再删除旧对象。保留 `.meta` GUID 和正确脚本引用，Windows Unity 中检查 Missing Script、事件持久监听和 Inspector 引用。

### 10.9 异步与数据契约

- 每次连接/模式变更分配本地 operation generation，旧请求完成后若代次不匹配，释放资源并忽略 UI 更新。
- 所有 Unity 对象更新切回主线程；网络线程只提交数据/事件。
- Connect、Disconnect、Pause、StopVideo、StopVoice 可重复调用且结果一致。
- 停止请求先关发送门，再清理媒体/网络；动画不能延迟实际停止。
- `QuestPacketEnvelope` 的 session 当前按进程生成、sequence 按流递增。UI 会话代次不应偷偷替换为新协议 session；若将来需要更改，必须和 MORLA 接收器一起定义。
- 保留单调时间校时，不以操作系统 UTC 时间直接判定跨机器的源数据新鲜度。

## 11. 配置持久化与迁移

使用带版本号的配置文件或类型化存储，区分“草稿”“已保存”“当前生效”。

旧键迁移包括 `SavedProtocol`、`SavedIP`、`SavedPort`、`SavedHandMode`、`SavedMixed`、`SavedIobt`、`Saved90Hz`、`SavedVoiceMic`。其他未以旧键保存的 UI 选项，从明确的旧场景默认/现有行为建立迁移值，不虚构它们曾被保存。

- Mixed=true → 混合输入；否则 IOBT=true → 全身与当前输入；两者 false → 标准输入。
- 若旧值同时为 true，沿用当前加载优先 Mixed 的结果，并在迁移日志记录冲突，不反复提示用户。
- 保留用户已有 IP/端口、刷新率和语音 opt-in 意图。
- 新版默认隐藏诊断面板和骨骼点；“协议调试元信息”的迁移保持原行为，写清两者不同。
- 显示类设置立即生效并节流保存；地址/模式等影响会话的设置显式应用，失败不把草稿标成生效。
- 已保存配置重新加载时不触发一串控件事件去重连；先恢复模型，再无通知更新控件，最后由协调器决定是否连接。
- 配置损坏时备份旧文件、回到安全默认并提示，不导致启动黑屏。
- 保存成功显示轻量“已保存”；关闭窗口不隐式应用未提交地址，保留草稿并明确“尚未应用”。
- 增加 `onboardingVersion`；升级只显示一次必要改版提示，不每次打开应用都重新引导。

## 12. MORLA 对接：哪些首版能做，哪些需要下游修改

### 12.1 Quest 端独立完成

可以完成：直接进透视、工具栏、设置侧栏、配置保存、本地追踪预览、位姿暂停/恢复、独立视频观察、语音状态提示、可读错误、诊断折叠、启动埋点。

保持现有位姿与语音协议、视频信令行为。真实机器人上使用“打开设置自动暂停发送”之前，仍须验证现有 MORLA 的失流保护与重新接管行为；这不是凭 Quest 代码能证明的。

### 12.2 需要 MORLA 配合的目标能力

- 实时显示机器人使能、跟随、采集、控制权、阻塞原因和状态更新时间。
- 点击“暂停跟随/恢复跟随”并获得明确结果。
- 连接恢复后留在非跟随态，确认新控制会话或重新对齐后再恢复。
- 主机声明必要数据源、必要视频、坐标模式与可用命令，Quest 据此禁用不支持的操作。

建议另设**版本化控制/状态通道**，或在已有、经确认可扩展的主机控制通道中实现。不要向现有位姿文本行任意夹入 UI 命令；也不要直接占用 8001 或 8765 假定它们支持所有控制消息。具体复用方式与端口必须阅读 MORLA 实现后确定。

最小逻辑契约建议包括：

- 状态：协议版本、主机身份、单调递增状态序号、当前控制会话、enable/follow/recording、控制所有者、允许命令、阻塞原因。
- 请求：唯一 requestId、控制会话、命令、必要前置条件。
- 结果：requestId、accepted/confirmed/rejected、原因、结果状态序号。accepted 不代表动作完成。
- 连续性：心跳、接收时刻、新鲜度判定、断线/过期转 Unknown；阈值由双方共同配置。
- 幂等：相同 requestId 重试不能重复触发采集或接管；过期请求不能在重连后执行。
- 控制归属：沿用 MORLA 已有授权/控制权规则，不因 Quest 能连上 socket 就授予运动控制。

这部分未检查下游仓库，名称是建议契约，不能标成 MORLA 已存在接口。也不承诺将首次使能/工作位从现有 Web 流程迁到 Quest；那是另一项明确功能范围。

## 13. 分阶段执行与完成条件

按可验证的结果推进，不把启动、协议、引擎升级和 UI 改版一次混在同一提交。

### 阶段 A：基线与启动清理

工作：记录当前 APK/源码对应关系；采集冷/热启动、帧率、发送节奏；检查三类 Splash；增加初始化埋点；最小工作区首帧。

完成条件：无外部服务时仍能进入透视；明确 Logo 的各阶段耗时；没有人为增加等待；Windows Unity 无编译错误。若当前 APK 与 `c0fcf73` 不对应，先保存可比较的基线构建。

### 阶段 B：业务与旧 UI 解耦

工作：引入类型化设置和状态快照；区分追踪/发送；加入发送门；逐个迁移原 `isStreaming` 读取者；处理取消、重复调用与后台恢复。

完成条件：不开旧菜单也能使用保存配置；不联网能看到本地追踪；关闭旧 UI 不引起空引用；发送 payload 与基线一致；原有四类追踪通路均可验证。

### 阶段 C：新工具栏与设置窗口

工作：实现 6 个设置页、通用控件、TMP 中文字体、输入仲裁、混合模式 UI 射线兼容、窗口重定位、配置迁移。

完成条件：全部原菜单选项有明确去处；手与手柄能操作；设置关闭不停止视频；设置操作不输出机器人输入；恢复发送必须明确触发。

### 阶段 D：媒体独立与视觉打磨

工作：视频独立观察、关键视角策略、断流提示、语音独立状态与非阻塞停止、日志降频、对比和布局适配。

完成条件：语音故障不拖垮其他链路；视频故障按明确策略处理；长中文消息和多相机布局可读；持续运行没有明显性能退化。

**A–D 为首版交付范围。** 该版本可显著改善日常体验，不需要先实现机器人新控制协议。

### 阶段 E：MORLA 状态与跟随控制闭环

工作：读取下游实现，确定控制契约，接入状态订阅、暂停/恢复确认、控制权、新会话与重新对齐策略；再评估自动连接与不中断遥测的 UI 交互。

完成条件：界面显示与机器人真实状态一致；丢回执、断网和重连不会出现假成功或自动恢复运动。自动化流程只有通过该阶段验证后才开放。

### 阶段 F：可选增强

近期不阻塞首版的项目：主机发现/二维码配置、腕部快捷入口、多机器人 Profile、全新画质档、纯手/纯手柄过滤策略、远端日志聚合。每一项都有额外 SDK 或下游依赖，应独立排期。

## 14. 验收清单

### 14.1 用户流程

- [ ] 首次安装：主机未启动，仍能进入透视；小引导可跳过；无强制大菜单。
- [ ] 再次启动：恢复主机和追踪偏好；不重复引导，不自动跟随。
- [ ] 麦克风/身体权限拒绝：其余功能仍可操作，有清楚的补救入口。
- [ ] 已配置主机：从工作区开始发送不超过一次主操作；缺配置时出现必要表单。
- [ ] 左手 Menu 键能唤出 UI；不会关闭可用视频或把整个应用退回旧菜单。
- [ ] 手部、双手柄、混合、全身模式下都能进入和关闭设置。
- [ ] 打开设置、点击开关、拖动窗口、输入 IP 的动作不进入机器人命令输出。
- [ ] 关闭设置、重新戴上头显、网络恢复不会自动恢复发送/跟随。
- [ ] UI 回到面前不改变发给机器人的坐标原点。

### 14.2 模式与数据回归

- [ ] 标准输入、Mixed、IOBT 三种配置逐一验证；Mixed 与 IOBT 不共启。
- [ ] 双侧/左侧/右侧选择对手部和手柄一致生效；身体通道语义不被误改。
- [ ] Mixed 运行时的 UI active-state 不因组合输入而全失效。
- [ ] IOBT 等待参考姿态、丢失参考、切回世界系时不会混发跨系数据。
- [ ] 原 wrist/landmarks/controller/buttons/head/body payload、数值精度和坐标约定保持。
- [ ] `@q3m`、按流 sequence、session 与 `@q3sync`/ACK 行为兼容当前 MORLA。
- [ ] 隐藏调试 UI 不改变协议调试元信息；日志开关影响可解释。
- [ ] 在相同模式与刷新率下比较发送间隔中位数/p95、有效样本率、下游拒包数；无未经解释的退化。

### 14.3 连接与故障注入

- [ ] USB 转发缺失、主机拒绝、Wi-Fi 不可用、错误 IP/端口均有对应提示。
- [ ] UDP 未确认接收时不会显示“主机已接收”。
- [ ] 连点开始、连接中取消、换 IP、视频尚在 await 时断开，均不会由旧回调重启会话。
- [ ] 位姿服务停机、8001 停机、8765 停机分别验证，不混成同一全局错误。
- [ ] 关键相机冻结时触发对应暂停策略；可选相机失效只影响自己。
- [ ] 应用失焦/后台/摘下头显立即关闭发送门和录音；回前台保留恢复门。
- [ ] 下游旧姿态、旧音频、旧控制命令不会在恢复后被补发。
- [ ] MORLA 未接入状态服务时始终使用 Unknown/未接入语义。
- [ ] 接入后测试拒绝、超时、重复 requestId、状态过期、控制权转移与重连。

### 14.4 视觉与性能

- [ ] 明亮房间、暗处、复杂透视背景下文字可读；状态不只靠颜色。
- [ ] 中文反馈、长错误、较大字号不溢出；没有方框缺字；交互命中区足够大。
- [ ] 视频宽高比和 FOV 不变，没有“放大镜”回归。
- [ ] 设置窗口首次打开和重复打开无明显卡顿；滚动、下拉、键盘和拖动均可用。
- [ ] 90 Hz 对应每帧约 11.1 ms、72 Hz 约 13.9 ms；CPU/GPU 均按实际瓶颈测量。UI 增量目标先设约 1 ms 以内，并以实测调整。

## 15. 开始实施前保留的核实项

这些项不妨碍完成 UI 设计，但会影响具体实现和真实机器人部署：

1. 当前设备 APK 是否与本次源码一致；用户所见 Logo 属于哪一层，冷启动各阶段实际耗时是多少。
2. MORLA 对输入断流、过期、重新接入和坐标切换的行为；是否已有状态/控制权接口。
3. 日常主要使用全身模式还是 Mixed；需要哪些输入作为强制条件；默认主相机是否是操作唯一视角。
4. SDK 72 下 hand ray 在 SHAC 与 IOBT 中的实际可用性，是否需要替换 active-state 组件。
5. Meta 当前在线多模态文档的软件版本段写的是 Unity 6000.0.66f2 及以上，而本项目是 6000.0.65f1。它不能直接证明现有构建不可用，但意味着不能照抄当前文档 API/兼容结论；先保持现版本做回归，升级作为独立事项。[Meta：版本与兼容性](https://developers.meta.com/vr/documentation/unity/unity-multimodal/)
6. 当前代码和 README 的关节数/计时器说明漂移，另外整理修正，不借 UI 改版改变遥操基础算法。

## 16. 推荐的首版交付结果

完成后，用户看到的应当是：

**打开 MORLA XR 即进入透视工作区，中央留给机器人画面；下方只有少量常用操作。设置以独立窗口打开，左侧分类、右侧调整。保存一次配置后，日常只需开始/暂停发送。追踪、视频、语音各自说明状态，机器人控制状态由 MORLA 确认。**

代码交付应同时包含新版场景/prefab、配置迁移、状态与输入门控、中文字体、通道异常处理、Windows 构建记录和 Quest 验收记录。设计稿中出现的控件必须对应真实功能；尚未接入的跨端能力以明确不可用状态呈现。
